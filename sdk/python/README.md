# Dilock — Python

Status: draft-1 Redis and etcd SDKs plus a draft Consul HTTP/KV session adapter. Consul remains experimental, requires leases of at least 10 seconds, and its per-key LockIndex fence requires operators to retain Consul lock entries; Consul source adapters and facades now exist across the catalogued SDKs; cross-language interoperability and per-route validation remain incomplete. The etcd adapter targets the official v3.7.2 gRPC wire API using the upstream-derived, license-preserved protocol subset under `src/dilock/_etcd_proto/`. Redis strict mutual exclusion assumes one writable authority that preserves lock state; asynchronous replica promotion can lose a held key and is unsupported for this guarantee. This does not establish quorum, failover, restore safety, or protected-resource fencing.

Design: asyncio; structural Protocol; async context manager; dataclasses for options; native exceptions; py.typed.

Install from this checkout with `python -m pip install '.[redis]'` or `python -m pip install '.[etcd]'` or `python -m pip install '.[consul]'`. Use `RedisProvider(url, epoch="...")`, `EtcdProvider(endpoint, epoch="...")`, or `ConsulProvider(endpoint, epoch="...")` for the default namespace and default acquisition policy; pass `namespace` and immutable `default_acquisition=AcquireOptions(...)` to configure them. Each handle's `hold()` async context manager acquires and releases using that same provider; explicit `async with await handle.acquire(...)` and `lease.release()` remain supported. Handles and leases are bound to their creating asyncio loop. `try_acquire` returns `None` only for acknowledged contention. After Redis reports contention, the SDK makes one bounded, read-only `TYPE` request: strings and expired keys remain busy, other key types raise `ProtocolMismatch`, and a failed classification raises `BackendUnavailable`. After a dispatched Redis `SET`, a lost reply or timeout raises `AcquisitionUnknown` even if owner-checked cleanup is acknowledged, because the original `SET` could still execute later. Cancellation remains `CancelledError` only when owner cleanup is acknowledged; otherwise the SDK raises `AcquisitionUnknown`. Backend errors remain distinct from contention. Every etcd acquisition receives a fresh server lease and owns its native Lock key. Release spends one independent cleanup budget across Unlock and LeaseRevoke together; the second RPC receives only the monotonic time remaining after the first. Process exit relies on server TTL. `lease.lost` is local notice and does not cancel arbitrary work. Redis auto-renewal is opt-in; etcd keepalive runs while the native Lock RPC waits. etcd exposes an epoch-scoped `create_revision` fence; the protected resource must atomically enforce it. A successful scope exit requires release outcome `RELEASED`; `ALREADY_NOT_OWNED` and `UNKNOWN` raise `ScopeReleaseError` with the exact outcome. If the body raises, its exception stays primary and cleanup diagnostics are reported through the optional callback (or Python logging). These adapters do not claim exactly-once effects or that lease expiry stops old processes. Consul details, including lock-key retention requirements, are in `../../spec/backends/CONSUL.md`.

For etcd release, `RELEASED` requires exact-key ownership evidence and acknowledged native `Unlock` and `LeaseRevoke`. A confirmed missing/mismatched key, absent lease, or acknowledged unique-lease revoke after confirmed ownership returns `ALREADY_NOT_OWNED` when those full release acknowledgements are unavailable. Uncertain ownership or cleanup returns `UNKNOWN`; an `Unlock` acknowledgement alone is insufficient. Repeated calls return the cached outcome and do not replay either operation. Cleanup after an acquisition failure uses one monotonic budget: stopping the waiter keepalive consumes part of that budget, and LeaseRevoke receives only the remainder. If no time remains or revoke is unacknowledged, acquisition cleanup raises `AcquisitionUnknown`; the attempt lease then expires under the configured etcd TTL. Ownership verification and keepalive shutdown are included in the overall acquisition wait; a late positive acquisition returns `WaitTimeout` only after confirmed abandonment, otherwise `AcquisitionUnknown`.

Before use, an administrator must explicitly provision matching draft-1 metadata; ordinary clients never create or repair it. For Redis, use `python tools/provision.py --endpoint redis://127.0.0.1:6379 --namespace app --epoch deployment-2026-01`. For etcd, create `/dilock/namespaces/<namespace>/meta` with profile `etcd-native-lock-v1` and the approved epoch. For Consul, use `python tools/provision_consul.py --endpoint http://127.0.0.1:8500 --namespace app --epoch deployment-2026-01`. See the [Consul quickstart](../../docs/examples/python-consul/quickstart/README.md), [Redis quickstart](../../docs/examples/python-redis/quickstart/README.md), and [etcd quickstart](../../docs/examples/python-etcd/quickstart/README.md). Review `../../spec/backends/REDIS.md`, `../../spec/backends/ETCD.md`, and `../../spec/backends/CONSUL.md` for profile limits. The Consul draft was exercised with HashiCorp Consul 1.22.5 as a single-member functional server; this says nothing about quorum, failover, or restore safety. The tested etcd process has the same single-member evidence boundary. Distribution: local project package only; nothing has been published.

Install test dependencies with `python -m pip install '.[test]'`. Build/test: `python -m pytest`, `python -m mypy src/dilock`, `python -m ruff check src tests`, and `python -m build`. Real Redis tests require `DILOCK_REDIS_URL`; etcd tests require `DILOCK_ETCD_ENDPOINT`, `DILOCK_ETCD_NAMESPACE`, and `DILOCK_ETCD_EPOCH`; Consul tests require `DILOCK_CONSUL_ENDPOINT`, `DILOCK_CONSUL_NAMESPACE`, and `DILOCK_CONSUL_EPOCH`. Skipped integration tests are not evidence. Client versions are pinned in their optional extras.

Use `../../spec/` for semantics and `../../docs/api/LANGUAGE-DESIGN.md` for design. Do not publish before real backend, conformance and installed-package tests pass.
