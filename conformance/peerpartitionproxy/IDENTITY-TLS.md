# Identity-aware peer filtering

The peer proxy has an opt-in mutual-TLS mode for local fault tests. It authenticates the incoming peer certificate, requires an exact leaf-certificate pin for the certificate common name, and checks a directed source-to-destination ACL before opening the upstream TLS connection. For an allowed connection, the proxy presents the destination member certificate to the source and presents the source member certificate to the destination. Both TLS legs verify against the supplied test CA.

Enable the mode with `--identity-member-id`, `--identity-peer-ids`, `--identity-ca-file`, and `--identity-cert-dir`. The certificate directory contains `<peer-id>.crt` and `<peer-id>.key` for the destination and every listed source identity. The source list must exclude the destination itself so self-links are not admitted. IDs are restricted to ASCII letters, digits, `.`, `_`, and `-`; certificate common names and DNS subject alternative names must equal their filenames' peer IDs. The CA and leaf certificates should be generated for one local test run and retained only with that run's evidence.

The synchronous control channel accepts `block-peer` and `allow-peer` with a `peer_id`. A block closes existing streams authenticated as that source and denies new handshakes before they reach the destination. State snapshots expose the destination identity, sorted allowed source identities, active streams, successful upstream TLS connections, blocked attempts by source identity, and ordered peer events. Events record the observed leaf SHA-256 fingerprint; `identity` is populated only when that exact fingerprint was pinned to the identity. Rejected handshakes record an unverified certificate common name separately, so a self-asserted name is never reported as authenticated identity.

This is a test proxy that terminates and re-originates TLS; it is not a transparent packet filter and must not be used in a production topology. For three members, exclude the three self-links: the six valid directed edges consist of two permitted majority-to-majority edges and four blocked majority/minority crossing edges. The Go fixture observes and fingerprint-checks all six. The etcd harness wires per-run certificates, peer mTLS flags, and directed ACL acknowledgments. SDK workers first connect and validate metadata while the full cluster has quorum; the harness then verifies the six-edge fingerprint matrix before issuing fault operations. After healing, it also requires all six directions to forward. A first native etcd run verified the matrix and majority quorum but stopped when a minority-targeted TypeScript worker attempted its initial metadata read after partitioning; the harness now initializes all workers before applying ACLs. A complete SDK fault run remains outstanding.
